What the numbers mean

Every row in this report comes from the usage block your AI provider returns for each request. Three counters decide what you pay — here is exactly how each one works and how this report treats them.

⬆ Input tokens (billed at the input price)

Everything the model reads on a request: your prompt, the whole conversation so far (every earlier message is re-sent each turn), tool definitions, and any pasted documents. Input grows as a session gets longer — request #50 re-reads requests #1–49, which is why long sessions burn far more than the visible typing suggests.

⬇ Output tokens (billed at the output price — usually 3–5× input)

Everything the model writes: the visible answer, plus reasoning/thinking tokens for reasoning models (GLM, o3, Claude extended thinking). This report counts reasoning inside output because providers bill it that way — a short answer that "thought" for 4,000 tokens costs 4,000 output tokens. Tool calls the model emits (the JSON it writes to run a command or edit a file) are output too.

📚 Cache read (billed at a fraction of input — typically ~10%)

Providers cache the unchanged prefix of your conversation. On the next request, everything byte-identical to last time is read from cache at the discounted rate instead of full input price. Cache read is not extra tokens — it is your input getting the cheap rate. That's why an ongoing session is much cheaper per turn than re-explaining everything in a fresh chat. The cache breaks when you edit earlier messages, switch models, or idle past the provider TTL (minutes) — the next request then re-pays full input.

✍️ Cache write (billed slightly above input, ~1.25×)

The fee for creating cache entries: the first time a prefix is seen (or after a cache break) those tokens bill as cache write instead of plain input. Next request, the same prefix returns as a cheap cache read. Over a multi-turn session: ~1.25× once per prefix, ~0.1× for every reuse after — a large saving when turns share context.

How a real request bills

Turn 2 of a session where turn 1 built 10,000 tokens of context and you typed 200 new tokens: 10,000 cache read (cheap) + 200 input (fresh text, also written to cache) + the answer as output. Turn 3 re-reads all 10,200 from cache again. The whole economy: keep sessions coherent (cache hits), avoid re-pasting the same content (it becomes fresh input every turn), and remember thinking time bills as output.

The fine print

  • Counts are provider-reported, not estimated: the app reads the usage blocks your providers already wrote into the session logs. Tokenizers differ per model, so the same text can tokenize differently — the provider's number is the one you pay for.
  • Costs are estimates: they use the per-model USD prices in Settings. A new model id not in the table falls back to default — edit that row to match your plan.
  • Retries count: a provider-retried request can appear as its own usage row — one expensive-looking request may be two attempts.
  • Non-token fees (per-search charges, subscriptions) are not in the session logs and therefore not in the estimates.
  • Image inputs bill as tokens and are included when the log reports them; most CLI logs only carry numeric totals.
  • Flat plans: if your plan is a subscription rather than per-token, treat "Est. cost" as a usage meter, not money.
